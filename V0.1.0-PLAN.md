## 2. Custom signals

Send an arbitrary POSIX signal to a running service process — e.g. `SIGHUP` to reload config, `SIGUSR1`/`SIGUSR2` for custom app signals.

### Config

```ts
// UserServiceConfig gains an optional field:
signals?: Array<{ label: string; signal: string }>;

// Example:
signals: [
  { label: "Reload config", signal: "SIGHUP" },
  { label: "Reopen logs",   signal: "SIGUSR1" },
]
```

### Backend changes

**`types.ts`**
- Add `signals?: Array<{ label: string; signal: string }>` to `UserServiceConfig` and `Service`.

**`service-manager.ts`**
- Add `sendSignal(serviceID: string, signal: string): void`
  - Guard: service must be `running`; signal string validated against a small allowlist (SIGHUP, SIGUSR1, SIGUSR2, SIGWINCH — anything in `os.constants.signals`)
  - Calls `service.process.kill(signal)`
  - Logs `Sent ${signal} to ${service.name}` as a system log entry

**`web-socket-handler.ts`**
- New `action: "send_signal"` case, payload `{ action, serviceID, signal: string }`
- Delegates to `serviceManager.sendSignal(serviceID, signal)`

**`http-handler.ts`** / **`index.ts`**
- Pass `signals` through in `sendInitialState` so the frontend knows which signals are configured per service.

### Frontend changes

**`types.ts`**
- Add `signals?: Array<{ label: string; signal: string }>` to `ServiceConfig`.

**UI** (service card / control bar)
- When `signals` is non-empty and service is `running`: render a "Send signal" dropdown button next to Stop/Restart.
- Selecting an entry sends `{ action: "send_signal", serviceID, signal }` over WebSocket.
- Disabled (greyed) when service is not running.

- [ ] `service-manager.ts`: add `sendSignal` method with signal validation
- [ ] `web-socket-handler.ts`: add `send_signal` action case
- [ ] Pass `signals` per service in `sendInitialState`
- [ ] `types.ts` (frontend): add `signals` to `ServiceConfig`
- [ ] Frontend UI: signal dropdown component

## 3. `dependsOn` — startup ordering

A simple dependency list per service. "Start All" starts services in dependency order; "Stop All" stops them in reverse order.

### Config

```ts
// UserServiceConfig gains an optional field:
dependsOn?: string[];

// Example: api-server waits for db to be running before it starts
{ id: "db",         ... },
{ id: "api-server", dependsOn: ["db"], ... },
{ id: "worker",     dependsOn: ["db", "api-server"], ... },
```

### How it works

**Topological sort** — computed once in `ServiceManager` constructor from the `dependsOn` graph. Result is stored as `startOrder: string[]` (array of service IDs).

- If a cycle is detected: log a warning, fall back to config array order, continue normally.
- If a `dependsOn` entry references an unknown ID: log a warning and ignore that entry.

**Start All** — the backend sends services in `startOrder` sequence in the `initial_state` WebSocket message. The frontend's existing sequential loop already iterates in the order services are received, so dependency ordering is free with no frontend logic changes.

Because "Start All" is already sequential (sends start, waits for `running` before moving on), a dependent service naturally doesn't start until its dependency is confirmed running.

**Dependency failure during Start All** — when a service reaches `error`/`crashed`, instead of aborting everything (current behavior), the frontend skips only services that (directly or transitively) depend on the failed service, logs a system message like `Skipping api-server — dependency 'db' failed`, and continues starting unrelated services. A toast summarizes which were skipped.

The backend sends a `dependsOn` map in `initial_state` so the frontend can compute transitive dependents without extra roundtrips.

**Stop All** — `stopAllServices` currently stops in parallel. Change to sequential in *reverse* `startOrder`: dependents stop first, then their dependencies. Each service already does SIGTERM → 5s → SIGKILL, so if a service hangs it gets force-killed and shutdown continues to the next one — nothing blocks forever.

- [ ] `service-manager.ts`: topological sort utility, store `startOrder`, warn on cycle/unknown ID
- [ ] `service-manager.ts`: emit services in `startOrder` from `getServices()` (or expose `startOrder` separately)

## 4. `beforeStart` hook

Run an async function before the service process spawns. It receives the resolved env, can log to the service's log stream, and can return a modified env. Errors are caught and put the service into `error` state — they do not crash the dashboard. If the user stops the service while the hook is running, an `AbortSignal` is fired.

### New status: `"initializing"`

Add `"initializing"` to the status union everywhere it is defined (types, frontend). State machine:

```
stopped / error
  → initializing   (beforeStart running)
    → starting     (process.spawn called)
      → running
  → error          (beforeStart threw)
  → stopped        (user stopped during initializing)
```

### Config

```ts
// types.ts — new type:
export interface BeforeStartContext {
  env: Record<string, string>;   // merged env that will be passed to the process
  log: (line: string) => void;   // writes a "system" log line to the service log
  signal: AbortSignal;           // aborted if user stops during initializing
}

// UserServiceConfig gains an optional field:
beforeStart?: (ctx: BeforeStartContext) => Promise<Record<string, string> | void>;
```

### Backend changes

**`types.ts`**
- Add `"initializing"` to `Service["status"]`.
- Add `BeforeStartContext` interface.
- Add `beforeStart?` to `UserServiceConfig` and `Service`.

**`service-manager.ts`** — `startService` change

Current flow:
```
guard check → set status "starting" → spawn
```

New flow:
```
guard check
→ if beforeStart defined:
    set status "initializing", broadcastStatus, addLog "Running pre-start hook..."
    create AbortController, store ref on service so stopService can abort it
    try {
      resolvedEnv = await beforeStart({ env: mergedEnv, log, signal })
      if signal.aborted → return (stopService already cleaned up)
      mergedEnv = resolvedEnv ?? mergedEnv
    } catch (err) {
      service.status = "error"
      addLog(`Pre-start hook failed: ${err.message}`, "system")
      broadcastStatus(serviceID, "error", err.message)
      return
    }
→ set status "starting" → spawn (same as today)
```

**`stopService`** — if service is `"initializing"`, abort the controller and set status `"stopped"`. The Promise from `beforeStart` is left to settle on its own; once aborted we just ignore any further return value.

Store the `AbortController` as a private property on `ServiceManager` (a `Map<serviceID, AbortController>`), cleared when the service leaves the `initializing` state.

### Checklist
- [ ] `types.ts` (backend): add `"initializing"` to status union, `BeforeStartContext` interface, `beforeStart` to `UserServiceConfig` and `Service`
- [ ] `service-manager.ts`: `initializing` state + `AbortController` map
- [ ] `service-manager.ts`: `beforeStart` invocation with env, log callback, signal
- [ ] `service-manager.ts`: `stopService` aborts controller when status is `"initializing"`
- [ ] `types.ts` (frontend): add `"initializing"` to status union
- [ ] Frontend UI: `"initializing"` status badge/display (same style as `"starting"`)
- [ ] Frontend `startAllServices`: treat `"initializing"` as in-progress (don't time out early)

## 5. Unit tests

The existing test file (`index.test.ts`) tests through the full HTTP/WS stack. For v0.1.0 we add a dedicated `service-manager.test.ts` that instantiates `ServiceManager` directly (no HTTP server needed, faster + isolated).

### Tests to write

**Existing behavior (regression coverage)**
- Service initializes with `stopped` status
- `startService` transitions through `starting` → `running` (mock spawn)
- `stopService` sends SIGTERM, falls back to SIGKILL after timeout
- `restartService` stops then starts
- `clearServiceLogs` truncates log array and broadcasts `logs_cleared`
- Log buffer respects `maxLogLines` cap

**Custom signals**
- `sendSignal` calls `process.kill(signal)` when service is `running`
- `sendSignal` is a no-op when service is not `running`
- Invalid signal strings are rejected

**`dependsOn`**
- Services with no `dependsOn` are unaffected
- Topo sort produces correct order for linear chain (a → b → c)
- Topo sort produces correct order for diamond (a → b, a → c, b → d, c → d)
- Cycle detected → warning logged, falls back to config order, no crash
- Unknown `dependsOn` ID → warning logged, ignored
- `stopAllServices` stops in reverse topo order

**`beforeStart` hook**
- Hook runs before spawn; env returned by hook is passed to `spawn`
- Hook logging calls `addLog` with `"system"` type
- Hook that throws → service ends in `"error"` state, spawn never called
- Service that is stopped during `"initializing"` aborts the signal and ends in `"stopped"` state; spawn never called
- Hook that returns `void` → original env used unchanged
